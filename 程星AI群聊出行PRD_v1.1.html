1项目背景

1.1 产品定位

一句话定位：程星AI新增"群聊出行分步规划"能力——用户将微信群聊讨论转发到同程App后，AI自动识别出行要素，并以对话式分步引导的方式依次推荐大交通、酒店、景点，每步给出推荐理由并支持即时预订；全部选定后整合生成ABC三套方案，自动计算人均均摊价格，通过H5投票收集群友意见，最终生成一键预订方案。

1.2 业务目标

目标衡量指标目标值
验证群聊→方案核心链路导入→方案生成转化率≥25%
驱动交易转化方案→下单转化率≥15%
提升跨品类交叉销售方案中交通+酒店+门票三品类同时预订占比≥30%
建立多人协作心智方案H5分享率/投票参与率分享率≥30%/投票率≥60%

1.3 核心价值

🧭

分步引导不遗漏

交通→酒店→景点依次推进，每步AI基于群聊偏好给出推荐，不像一次性大方案让用户信息过载

👥

偏好归因到人

AI识别"谁想坐飞机、谁想住外滩"，推荐时引用群友原话，让每个人的意见被看见

🗳️

投票代替扯皮

ABC方案+H5投票，组织者不用反复@人确认，群友点一下就行，投票结果直接驱动下单

1.4 应用场景

以5人朋友团国庆出游为典型场景贯穿全文：

A国庆去上海玩吧！我查了机票还行
E高铁吧，飞机延误怕了
B我要去迪士尼乐园！！
C住外滩附近吧，晚上能逛
D我想住迪士尼附近，第二天不用早起
E我觉得住虹桥火车站附近方便，返程近
A那就本周六出发，周一回来，3天2夜

群聊中7个人的偏好散落在对话里，组织者需要逐一记录、分别查询、再协调统一——这正是本功能要解决的问题。

2需求概述

2.1 用户痛点

痛点具体表现严重程度
群聊信息散落5-8人的出行讨论可能产生几十上百条消息，组织者要逐条翻看记录每个人的偏好高
偏好冲突难协调有人想飞、有人想坐高铁；有人想住外滩、有人想住迪士尼，组织者无法同时满足所有人高
多品类查询繁琐要分别打开机票/火车票、酒店、门票三个频道查询比价，再手动汇总中
方案确认效率低做好方案发群里，有人不回、有人改主意，组织者反复@人确认耗时数天中
预订分散易遗漏交通、酒店、门票分开下单，容易漏订或时间冲突中

2.2 业务价值

  • 用户价值：从"群聊讨论→手动整理→分别查询→反复确认→分散下单"的5步繁琐流程，压缩为"转发→确认→分步推荐→投票→一键预订"的线性流程
  • 商业价值：单次规划触达交通+酒店+门票三个品类，交叉销售机会显著；投票H5形成社交裂变，参与者回流同程
  • 差异化价值：竞品（飞猪帮帮、腾讯元宝）均无"分步推荐+偏好归因+投票决策"的完整闭环

2.3 版本范围

V1.0 核心范围：App转发接收 → AI识别要素（人数/日期/城市/个人偏好） → 对话式三步推荐（交通→酒店→景点） → ABC方案生成+人均均摊计算 → H5投票（含人均价展示）→ 一键预订方案生成。
不含：机票预订（火车票P0，机票仅展示对比）、小程序截图OCR入口（见产品方案v1.1，本PRD聚焦App主路径）、AA账单收款/结算跟踪（V1.5）。

6功能设计

6.1 聊天记录导入与自动识别

6.1.1 触发方式

微信群聊 → 长按多选旅行相关消息 → 点击"转发" → "更多" → 选择"同程旅行"App → iOS通过Share Extension / Android通过Intent ACTION_SEND接收文本 → 同程App自动打开程星AI对话界面，文本自动填入输入框并自动发送触发解析。

技术要点：
• iOS：Share Extension接收public.plain-text和public.url类型，通过App Group共享数据或URL Scheme传递给主程序
• Android：注册ACTION_SEND Intent Filter，接收text/plain类型
• 转发文本格式：微信多选转发保留"发送人：内容"结构，是偏好归因的基础

6.1.2 AI识别内容

AI解析转发文本后，需提取两类信息：

类别字段识别示例置信度处理
必要信息人数"5个人"→5；"我们一家三口"→3≥85%直接确认；60-85%高亮请确认；<60%追问
日期"10月1号出发3号回来"→10.1-10.3；"国庆3天2晚"→10.1-10.3
出发城市"从北京走"→北京
目的城市"去上海"→上海
个人偏好交通偏好+归因A："机票还行"→{person:A, type:flight, raw:"机票还行"}；E："高铁吧"→{person:E, type:train, raw:"高铁吧，飞机延误怕了"}每条偏好必须归因到具体发言人；无法确定发言人时标注"群友"

6.1.3 发言人标识

  • 从转发文本中提取发送人昵称（微信转发格式通常为"昵称：内容"）
  • 在程星AI界面中，每个发言人用不同颜色的圆形头像标签展示（A/B/C/D/E...），与群聊中的昵称建立映射
  • 后续所有推荐和方案中引用偏好时，均使用相同颜色标签标注发言人
  • 如转发文本中无法提取发送人（如粘贴文本场景），统一标注为"群友"，不做归因

6.3 Step1：大交通推荐

6.3.1 查询逻辑

  1. 使用确认后的出发城市、目的城市、出发日期，同时调用机票查询和火车票查询接口
  2. 机票：查询出发日期当天所有航班，取价格最低的1个班次作为推荐候选；另取时间最合适的1个作为备选
  3. 火车票：查询出发日期当天所有车次，优先取高铁/动车，取时间最合适的1个车次作为推荐候选；另取价格最低的1个作为备选
  4. 按人数计算总价（机票×人数、火车票×人数）

6.3.3 AI推荐逻辑

AI综合以下因素生成推荐和推荐理由：

  • 群友偏好权重：如有明确偏好，推荐理由引用原话（"E提到怕飞机延误"）
  • 价格对比：计算两种方式的差价，在推荐理由中显性化（"5人总价省¥635"）
  • 时间成本：对比总耗时（含提前到机场/车站时间），飞机虽飞行短但需提前2小时到机场
  • 日期因素：节假日航班延误率高，高铁准点率更高，作为推荐依据
  • 人数因素：5人团体，高铁座位可连座，飞机座位分散，作为隐性因素

推荐理由控制在2-3句话，先给结论再给依据，引用群友原话增加说服力。如群友偏好冲突（有人想飞有人想高铁），需在理由中承认分歧并给出折中建议。

6.4 Step2：酒店推荐

6.4.1 查询逻辑

  1. 从已确认偏好中提取所有住宿位置偏好（本例中3个：外滩、迪士尼、虹桥）
  2. 对每个位置，以该位置为中心，调用酒店搜索接口（按距离排序），取最近的3家酒店
  3. 查询条件：入住日期=出发日期，离店日期=返回日期（即10.1入住，10.3离店，2晚）
  4. 根据人数自动计算房型需求：5人 → 默认3间房（2间双床房+1间大床房），用户可调整
  5. 展示每家酒店的：名称、距离位置点、星级/评分、起价、房型组合总价（2晚）
💡 多位置偏好处理策略：群聊中出现多个位置偏好时，不做筛选，全部展示。AI推荐时综合考虑：哪个位置对多数人便利、哪个位置性价比最高、哪个位置靠近核心景点。最终ABC方案的差异主要来自酒店位置/档次的不同组合。

6.4.2 展示结构

6.4.3 AI推荐逻辑

从所有查询到的酒店中推荐1家，综合因素：

  • 偏好覆盖：优先选择能满足最多人需求的位置。如B要去迪士尼，住迪士尼附近可满足D和B两人
  • 交通便利：考虑到酒店位置与景点/车站的距离和交通时间
  • 性价比：在满足偏好的酒店中选择价格适中的（非最贵也非最便宜）
  • 评分/口碑：优先推荐评分≥4.5的酒店
  • 引用原话：推荐理由中引用群友偏好，如"C想住外滩附近，这家就在外滩核心区"

6.4.4 操作分支

与交通步骤一致：用户选择酒店后可"去预订"（跳转酒店预订页）或"继续看看景点"（暂存选择进入ATTRACTION状态）。用户也可在对话框说"换一家""看看更便宜的"，AI重新推荐。

  2. 调用门票查询接口，获取该景点在出行日期范围内的门票信息（价格/开放时间/预订规则）

6.6 ABC方案生成

6.6.1 方案差异化逻辑

ABC三套方案基于用户在分步推荐中的选择和群聊偏好，通过酒店位置/档次的不同组合产生差异化。交通方式和景点在三步中已选定（本例均为高铁+迪士尼），不作为方案变量。

方案生成规则：
1. 交通和景点为用户在Step1/Step3中的确定选择，三套方案保持一致
2. 酒店为主要变量：取群聊中提到的N个位置偏好，每个位置选1家酒店（AI推荐的那家），形成N套方案
3. 如群聊中只提到1个位置，则另生成2套备选（附近同档次+经济档），凑齐3套

5. 每套方案计算总价和人均价，AI推荐性价比最优的一套（不一定是最便宜的）

6.6.3 方案调整

  • 用户可在对话框中说"方案A换个便宜点的酒店"，AI局部调整方案A的酒店，其他不变
  • 用户可说"把高铁改成飞机"，三套方案的交通全部更新并重新计算价格
  • 调整后实时更新价格和人均均摊金额

6.6.4 费用均摊计算 v1.1新增

ABC三套方案生成后，系统自动为每套方案计算人均均摊价格，无需用户额外操作。

默认均摊规则（V1.0）：按人头均摊

人均费用 = （交通费总价 + 酒店费总价 + 门票费总价）÷ 成人数

说明：
• 成人 = 总人数 − 儿童数；儿童票/儿童占床费用计入总价，但除数只算成人（即儿童部分由同行成人共同承担）
• 是否儿童：从群聊识别"带孩子/小孩/我家娃"等表述，或用户在确认卡片中手动标注；无法判断时默认全部按成人计
• 交通：5人全部乘坐同一车次/航班，总价÷成人数
• 酒店：3间房2晚总价÷成人数（V1.0不区分谁住哪间，统一平摊；差异化按房间分摊V1.5）
• 门票：5人全部去同一景点，总价÷成人数

6.8.3 预订执行

  • 分别预订：点击每项"去预订"，携带预填信息（车次/日期/人数、酒店/日期/房型/间数、景点/日期/人数）跳转同程对应交易页，用户确认后下单
  • 一键预订：点击"全部一键预订"，依次跳转各品类交易页（火车→酒店→门票），每页预填信息，用户逐页确认下单。上一页完成后自动进入下一页
  • 价格刷新：进入预订前重新查询实时价格，如价格变动超过5%，弹窗提示"价格已变动，新价格¥XXX，是否继续？"
  • 预订状态同步：每完成一项预订，清单中状态更新为"已预订"并显示订单号
  • 部分完成：用户可只预订部分项目（如先订火车票，酒店和门票稍后再订），清单保留待预订项

6.8.4 预订后

  • 全部预订完成后，生成行程确认单，含每人应付均摊明细，可一键分享到群聊（方便大家转账给组织者）
  • 已预订的订单同步到同程"我的订单"中，可正常查看/退改；退改后均摊明细自动重算
  • V1.5迭代：差异化均摊（按房间/按参与分摊/自定义比例）、AA账单收款、结算跟踪

9风险与异常

9.1 风险列表

风险类型风险描述等级应对措施
技术iOS Share Extension传递文本到主程序不稳定，部分iOS版本可能截断长文本中通过App Group共享文件而非剪贴板传递；超长文本分段传递；iOS 13+全覆盖测试
技术偏好归因错误（把A说的话归因给B），导致推荐理由引用错误高上线前用真实群聊数据测试归因准确率；用户可在确认卡片中删除/修正偏好；归因置信度低时标注"可能是XX说的"而非确定归因
技术机票+火车票+酒店多接口并行查询，某一接口超时拖慢整体中各品类独立超时（5秒），某品类超时展示"查询中"骨架屏，其他品类先展示；超时后提供"重试"按钮
业务群聊中5人但只有3人投票，投票结果代表性不足中显示已投票/未投票人数；组织者可催促投票；投票率低于50%时提示"参与率较低，结果可能不代表多数人意见"
业务投票后到预订期间价格变动（尤其国庆高峰期），用户投诉高预订前必须刷新实时价格；价格变动超5%弹窗提示；方案卡片上标注"价格实时变动，以预订时为准"
业务酒店按位置查询时，"外滩附近""迪士尼附近"等模糊位置无精确POI，导致搜索结果不准中建立热门景点/商圈别名映射表（"外滩"→外滩POI坐标）；模糊位置时取该区域中心点搜索；展示距离让用户判断
数据投票H5无需登录，可能被刷票中基于微信OpenID限制每人一票；同IP限制投票频率；异常投票模式检测（如1秒内大量投票）
合规转发群聊消息涉及他人隐私，群友可能不知情中App接收转发后明确提示"聊天记录仅用于本次出行规划，不会存储"；投票H5中不展示完整聊天原文，仅展示偏好摘要（如"C想住外滩"）；偏好归因使用群昵称而非真实姓名
体验分步推荐流程过长（3步+方案+投票+预订），用户中途流失中每步展示进度指示（Step 1/3）；每步支持"跳过"和"你决定"快捷操作；已选信息可随时修改；方案生成后可直接预订不强制投票
业务均摊计算中儿童身份误判（该半价的按全价算或反之），导致人均金额错误中识别到可能有儿童时在确认卡片明确标注"含X名儿童"并让用户确认；儿童票规则按各品类官方规则执行（火车1.2m以下免票/1.2-1.5m半价、迪士尼儿童票按年龄）；明细中标注儿童费用行
业务价格变动后方案卡片人均价与预订清单不一致，用户质疑中方案生成时标注"价格实时变动"；进入预订流程前统一刷新一次价格，刷新后同步更新方案卡片、H5和预订清单中的人均价；H5通过版本号/时间戳判断是否需要刷新
